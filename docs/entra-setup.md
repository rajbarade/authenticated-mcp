# Owner-run Entra setup — not executed

No tenant changes are authorized as part of this implementation. Complete the following only when the owner decides to configure the pilot. Subscription Owner permissions do not prove Entra application/group privileges. Verify the selected tenant and permission to register applications and manage assigned security groups first. A personal Microsoft account alone does not establish a suitable tenant user.

1. At entra.microsoft.com, select the intended directory. Open **Entra ID → App registrations → New registration**. Name it `Portable-MCP-HelloWorld-API`; select accounts in this organizational directory only. Record tenant ID and application ID privately. Verify the app appears in this tenant.
2. Open **Manifest**. Set `api.requestedAccessTokenVersion` to `2`, save, and read it back. Do this before configuring the HTTPS identifier.
3. Under **Expose an API**, set Application ID URI to the exact future `MCP_PUBLIC_URL`, including `/mcp`. Add enabled delegated scope `mcp.access` with consent descriptions and a consent policy appropriate to the tenant. Record the full scope `<MCP_PUBLIC_URL>/mcp.access`. Verify identifier URI and scope are saved. Do not add app-only roles for this v1.
4. Open **Entra ID → Groups → New group**, type Security, membership Assigned, name `MCP-Authorized-Users`. Add the owner tenant user. Record Group Object ID, not display name. Verify membership from the group Members view.
5. In the API app, **Token configuration → Add groups claim → Security groups**. Ensure access-token group claims use immutable IDs. Do not select only groups assigned to the application. Verify the saved token configuration; actual token verification follows below.
6. Inspect the corresponding service principal in **Enterprise applications** (normally created automatically). Inspect **Properties → Assignment required?**; the intended custom-policy pilot uses Off. Do not silently change an existing application's setting. Do not assign a security group to an enterprise application through premium features.
7. Preregister separate OAuth client applications as required by each client UI. Use exact callback URI, authorization code with S256 PKCE, delegated permission to this API, and necessary tenant/user consent. Record IDs and redirect URIs in the private acceptance record. Client secrets, if required by that UI, belong there, not in this API or repository. See [client gates](oauth-clients.md).
8. After owner-approved HTTPS hosting, retrieve public resource metadata and the tenant v2 OIDC discovery document. Confirm exact issuer, authorization/token endpoints and trusted jwks_uri. Check the actual client can use advertised PKCE metadata before proceeding.
9. Obtain a delegated API access token using the registered OAuth client. Inspect locally without uploading it or logging it: verify cryptographic signature, iss/tid/ver, aud, scp, oid and group IDs. Record only the expected audience/configuration and pass/fail evidence, never the token. Set JWT_AUDIENCE to the exact observed API audience after confirming this is the intended API; this implementation does not assume it equals the application UUID or resource URL. ID tokens and Graph access tokens are unsuitable. Record that a wrong API audience is rejected.
10. Follow all live tests in [testing.md](testing.md), including a second non-member and fresh tokens after membership changes.

These steps follow the supplied specification and current [Microsoft MCP registration guidance](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id). If the portal rejects the URI or the actual token differs, stop and record the discrepancy; do not widen accepted issuers/audiences to make it pass. [Microsoft group-claim guidance](https://learn.microsoft.com/en-us/entra/identity-platform/custom-rbac-for-developers) describes group overage; this version deliberately denies it instead of calling Graph.
